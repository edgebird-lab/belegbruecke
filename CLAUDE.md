# Belegbrücke – Hinweise für die Arbeit am Projekt

- Portfolio-Projekt von Robin (Wirtschaftsinformatik, olbricht-digital). Repo `edgebird-lab/belegbruecke` ist **seit 11.11.2026 öffentlich** (Robins Freigabe), mit Release v0.1.0 und Installer. Alles im Repo ist sichtbar: nie Zugangsdaten, echte Belege oder echte Kanzleidaten committen. Keine Lizenz (alle Rechte vorbehalten, kostenlose Nutzung); Fremdlizenzen in `docs/lizenzen-dritter.md`. Die Website verlinkt `releases/latest/download/Belegbruecke-Setup.exe`: Diesen Asset-Namen in `release.yml` beibehalten. Neue Tags/Releases nur auf Robins Wunsch; keine GitHub Pages, keine Bereitstellung auf Servern, keine Mails.
- Spezifikation: `docs/spezifikation.md`. Fortschritt als Checkliste in `docs/stand.md`, nach jedem Schritt aktualisieren. Annahmen, bis Robin entscheidet: `docs/entscheidungen.md`. Phase 7: das Windows-Programm (7.2 bis 7.5) hat Robin am 11.11.2026 freigegeben; Docker (7.1) und jede Bereitstellung auf einem Server weiter nur nach seiner Freigabe.
- Sprache: Oberfläche, Bezeichner, Doku und Commit-Nachrichten auf Deutsch. Keine KI-Funktionen, keine Cloud, keine Telemetrie; Daten bleiben lokal. Keine Echtdaten: Testrechnungen nur aus den offiziellen Testsuiten oder selbst erzeugt.
- Fachlogik in `src/fach` ohne React und ohne Node-APIs (die Typprüfung der Oberfläche erzwingt das), Prüfung in `src/pruefung` (Node, Worker), Server in `src/server`, Oberfläche in `src/ui`. Node 24 führt die TypeScript-Dateien des Servers direkt aus; relative Importe deshalb immer mit Endung `.ts`.
- Vor jedem Commit: `npm run lint`, `npm test`, `npm run build`, `npm run e2e` (lokal mit Edge); bei Änderungen am Programm zusätzlich `cargo test`, `npm run programm:server-test` und `npm run desktop:test`.
- Ports: Vorschau und Browsertests 4184 (`strictPort`), Server 8784, nur `127.0.0.1`. Nie 4173 (Prozesslotse); mehrere Apps laufen parallel auf diesem Rechner.
- Prüfartefakte: `npm run vorbereiten` lädt die KoSIT-Releases mit Prüfsumme nach `vendor/` und `testdaten/kosit/` und kompiliert die XSLT zu SEF. Diese Dateien sind nicht im Repo. Java nur für den Referenzlauf (`npm run referenz`), nie zur Laufzeit.
- Postfach (IMAP) nur gegen einen lokalen Testserver in den Tests; keine echten Postfächer, keine Zugangsdaten.
- Windows-Programm (Phase 7, Weg A): Tauri-Hülle in `src-tauri`, Server als Sidecar (unveränderte `node.exe` plus Bündel aus `npm run programm:server`). Rust liegt in `/c/Users/Robin/.cargo/bin` (nicht im PATH); immer mit `CARGO_TARGET_DIR=C:/Users/Robin/AppData/Local/cargo-ziel` bauen (gemeinsam mit anderen Apps, cargo wartet bei Sperre). Die Sperre gilt nur für cargo: makensis arbeitet für alle Apps in `release/nsis/x64`; vor einem Installer-Build prüfen, dass keine andere App gerade einen baut (`Get-Process makensis`). Prüfen: `cargo test --manifest-path src-tauri/Cargo.toml`, `npm run programm:server-test`, nach `npx tauri build --debug --no-bundle` dann `npm run desktop:test` (CDP-Port 9337, sichert und restauriert die Programmdaten). `start.cmd` bleibt für die Browser-Fassung.
- Installer nur auf Robins ausdrücklichen Wunsch auf seinem Rechner ausführen (am 11.11.2026 gewünscht: installiert pro Benutzer mit Desktop-Verknüpfung); Testläufe mit dem Desktop-Test.
